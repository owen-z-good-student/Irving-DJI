1What this is

The FH2 Integration Skill is a domain expertise pack that installs into your AI coding assistant. Once installed, FlightHub 2 integration questions are answered through a validated methodology rather than from the model's recollection.

The problem it solves

Without itWith it
The AI may invent endpoints that don't existAnti-hallucination is enforced: uncertainty is stated, and you're pointed to official docs to verify
Public Cloud and On-Premises APIs get mixed togetherDeployment model is confirmed first; API boundaries stay separate
Emergency-response patterns get applied to routine inspectionScenario is confirmed first; the two workflows are designed independently
Official docs are scattered — unclear where to startCapability selection tables plus requirement-to-endpoint mapping
Generated code lacks safety guardrailsSignature verification, idempotency, authorization and audit are built into the baseline
In one sentence It doesn't write your business logic for you. It ensures the AI stays accurate, in-bounds, and safety-complete within the FlightHub 2 domain.

3Installation

Drop the entire fh2-integration-skill/ directory into your assistant's skills folder. No additional dependencies.

Claude Code / OpenCode

# Path depends on your environment
~/.claude/skills/fh2-integration-skill/
# or
~/.config/opencode/skills/fh2-integration-skill/

The skill then activates automatically on FlightHub 2 / DFR / inspection topics.

Cursor

Copy the contents of adapters/cursor-rules.md into a project rule file:

.cursor/rules/fh2-integration.mdc
Optional: attach an OpenAPI MCP If your environment has the FlightHub 2 / Apifox OpenAPI MCP connected, the skill reads real endpoints and schemas through MCP for requirement matching and code changes, instead of asking you to look them up. Without MCP it falls back to official documentation links. In neither case will it fabricate an endpoint.

4Core mechanism: two gates

This is the most important design decision in the skill. Before any API recommendation is made, two gates must be passed.

Gate 1 · Deployment
Which deployment model? Public Cloud / On-Premises / AIO
Determines API surface and authentication model. The three do not expose the same capabilities.
↓
Gate 2 · Scenario
Which workflow? DFR emergency response / Inspection & patrol / Both
Determines interface selection, data flow and security focus.
↓
Only then: the design
Architecture · Interface mapping · Implementation plan · Security guardrails · Test plan
Why the AI asks questions before answering This is deliberate. Deployment model changes which APIs exist; scenario changes which ones you should use. The skill is explicitly forbidden from inferring deployment model from token format, URL, domain or region — guessing wrong means handing you an architecture that cannot work.

How the two scenarios differ

DimensionDFR / emergencyInspection / patrol
TriggerExternal alarm, CAD dispatchPlan, schedule, cycle
TimingSeconds, urgentRoutine, periodic
Primary interfaceAutomated dispatch workflowWayline + scheduled task
Data flow focusLive video, human takeoverCapture → analyze → share
Post-processingOn-scene decision, evidenceAI / VLM defect detection, 3D reconstruction

5What it can help with

DFR / emergency response

  • Middleware from CAD or alarm systems into FlightHub 2 dispatch
  • Drone livestream into a VMS or command center wall
  • Telemetry into GIS / PSIM situational awareness platforms
  • Media and evidence archival pipelines

Inspection / patrol

  • Wayline upload, sync into the FlightHub 2 wayline library, scheduled task dispatch
  • Inspection media → AI / VLM defect analysis → third-party platform
  • 3D reconstruction and point-cloud result sync

Common

  • Event API callback reception and handling
  • Choosing between FlightHub Sync / OpenAPI / MQTT Bridge
  • Verifying Public Cloud vs On-Premises API boundaries
  • Integrating FlightHub 2 into an existing platform (adapter layer design)
  • Implementation plans, test plans, security guardrails

6How to ask

No special syntax. State the requirement normally. The examples below are copy-ready.

Capability discovery

We want to inspect electrical substations with drones. What can FlightHub 2 do here?

DFR integration design

We're on FlightHub 2 Public Cloud. Design a middleware that turns CAD alarms into drone dispatch.

Inspection integration design

We're on-premises. Design a middleware for scheduled thermal inspection of substations.

Integrating with an existing system

We already run an operations platform. We want FlightHub 2 capabilities inside it, not a second standalone system.

Endpoint mapping and code changes

I'm building livestream integration. Produce a requirement-to-endpoint match table and flag the gaps.
Tip If you already know your deployment model and scenario, state both in your first message (e.g. "we're on-premises, doing inspection"). That skips the two gates and goes straight to design.

Quick start

# Backend
cd examples/dfr-public-cloud-demo/backend
npm install && npm start        # defaults to http://localhost:3000

# Frontend (separate terminal)
cd examples/dfr-public-cloud-demo/frontend
npm install && npm run serve

Full steps are in QUICKSTART.md inside the demo; cloud deployment is covered in deploy/README.md.

You can trial real dispatch locally — no server required With just an organization key, localhost can issue a real dispatch — no cloud server, no public IP, no tunnel. Dispatch is an outbound-only request (browser → local backend → FH2 cloud), so it traverses NAT without issue. This is the fastest path from "reading docs" to "watching the dock open".
FeatureTraffic directionWorks purely local
DispatchYou → FH2 cloudYes
Event API callbacksFH2 cloud → youNo — needs public ingress
MQTT telemetryFH2 cloud → your brokerNo — needs public ingress
Wayline syncFH2 cloud → your S3 bucketNo — needs public ingress

The last three require FlightHub 2 to connect inbound to your machine. A tunnel (ngrok, cpolar) unblocks them.

Dispatch drives real hardware This is not a simulation — the dock opens and the aircraft takes off. Before dispatching, confirm airspace compliance and on-site human supervision, and prefer a test dock.

What you need to prepare

  • Organization key: FlightHub 2 → My Organization → Organization Settings → OpenAPI → copy key
  • Project UUID: obtain via the "list projects under organization" endpoint
  • (Optional) MinIO / S3, MQTT broker, streaming server
The demo is educational, not production-grade It deliberately omits production requirements (such as Event API signature verification and database persistence) to lower the cost of understanding. Using it as-is in production is unsafe. Read LIMITATIONS.md in the demo directory for the full list of known gaps and the production checklist.
About the map The demo picks a basemap from your browser locale (Amap for Chinese, Google otherwise). Every basemap carries a coordinate-system offset warning — the map position is not the aircraft's actual flight position; always treat the dock location as your reference. The Google tiles used are an unofficial endpoint, for demonstration only; production must use the official API.

8Safety boundaries

The skill enforces a set of hard constraints. Knowing them helps you judge how much to trust a given output.

When the AI will stop and ask

TriggerWhat it needs from you
Deployment model unknownPublic Cloud / On-Premises / AIO
Authentication unclearToken / OAuth / SSO, and which values are placeholders
Flight control, dispatch, payload or device configuration involvedAuthorized environment, human-in-the-loop, safety review path
Touching a real customer systemExplicit authorization and target environment
Endpoint not confirmed in documentationVerification against official docs

What it will never do

  • Fabricate endpoints, request fields, event types or MQTT topics
  • Mix Public Cloud and On-Premises APIs
  • Recommend On-Premises-only capabilities for Public Cloud
  • Treat AI recognition output as directly actionable
  • Omit human-in-the-loop or geofencing flight-safety constraints
If the AI says "I cannot confirm this capability" That is by design, not a limitation. Telling you honestly and pointing to the official documentation is more valuable than inventing a plausible endpoint that doesn't work.

10FAQ

Why does the AI keep asking questions instead of answering?

Because deployment model and scenario fundamentally change which interfaces are available. This is the core design, not verbosity. State both in your first message to skip the gates.

The knowledge files are in English. Can they be translated?

Human-facing docs (README, usage guides, eval runbook, demo docs) have Chinese versions. SKILL.md and references/ are behavioral constraints read by the AI and are deliberately kept in English — instruction-following precision is higher, and it avoids conflicting rules from drift between two language copies. To understand any file, just ask the AI to explain it in your language.

Can I use the endpoints the AI gives me directly?

Not in production. The skill marks what needs verification. Confirm exact request bodies, response fields and permission requirements against the official Apifox documentation before shipping.

Can I adapt the demo into our own system?

Yes, but treat it as an adapter-layer skeleton, not a finished product. See ARCHITECTURE.md in the demo directory for how each module maps to the knowledge base, and what to add on the way to production.

Does this work for on-premises deployments?

Yes. The skill covers Public Cloud, On-Premises and AIO, and keeps their API boundaries strictly separated. Note however that the bundled demo targets Public Cloud — on-premises has a broader interface surface and may use a different authentication model, so don't copy the demo code directly.
