## 二、总入口

### `SKILL.md`

技能主文件，AI 每次都会先读它。包含：

- **frontmatter**：技能名、描述、触发条件（决定这个技能什么时候被激活）
- **两道 Gate**：部署 Gate（公有云 / 私有化 / AIO）→ 场景 Gate（DFR / 巡检）
- **Karpathy 式执行原则**：先思考再写码、简洁优先、外科手术式改动、目标驱动
- **5 个 STOP 检查点**：部署未知、认证不明、涉及生产控制、操作真实系统、端点未验证
- **SOP 五步流程**：确认上下文 → 选接口 → 应用部署边界 → 出架构设计 → 出代码指引
- **输出规范**：完整的 7 节架构模板 + 轻量的「需求↔端点 match 表」模板
- **OpenAPI MCP 优先规则**：有 MCP 就优先用 MCP 读真实端点

**什么时候起作用**：每一次对话。

## 三、`references/` 逐个文件

按**优先级**（AI 的读取顺序）排列。

### 1. `api-guardrails.md` — 红线与反幻觉规则

**优先级最高的文件。** 定义了什么绝对不能做：

- 两道 Gate 的强制要求（部署优先、场景其次）
- 5 个 STOP 检查点的触发条件与响应格式
- 禁止混用公有云与私有化的 API
- **反幻觉规则**：不得编造端点、请求体、响应字段、事件名、MQTT topic、控制指令
- 安全最低要求：token 存储轮换、权限范围、幂等、重试、验签、审计日志
- DFR 安全护栏（人在回路、可人工取消、地理围栏）+ 巡检安全护栏（AI 结果需人工复核）
- 需要保留的既定技术细节（MQTT 频率 0.5Hz、`x-dji-signature` 用 HMAC-SHA256 等）

**什么时候起作用**：全程。任何回答都不能违反这里的规则。

### 2. `fh2-openapi-v2-public-vs-private.md` — 部署边界决策

**第一道门的依据。** 讲清公有云和私有化到底差在哪：

- 部署决策树
- 公有云定位、可用接口清单、认证方式（`X-User-Token` + `X-Project-Uuid`）
- 私有化定位、可用接口清单、认证方式（可能是 OAuth 2.0 / SSO / 本地账号）
- AIO 定位（按私有化处理）
- **绝不可跨越的边界**，含 4 个"错误示例"：给公有云推荐 `paas.js`、把私有化端点用在公有云、从 URL 推断部署、说 Event API 仅私有化

**什么时候起作用**：用户问 API、问能不能做某件事时。

---

### 3. `fh2-openapi-v2-private-default.md` — 私有化 API 能力全景

私有化「默认模块」的能力地图：

- 通用术语表（`sn` / `gateway_sn` / `project_uuid` / `bid` / `tid` 等）
- **能力矩阵**：健康检查、存储 STS、安全、项目管理、组织管理、设备管理、实时控制、飞行任务、航线、地图、直播、媒体、模型——每一项都标注了与 DFR 的关联
- 私有化设计要点：控制权很重要、设备配置 API 属高危、飞控需人工监督、直播与媒体是集成锚点
- 待核验的端点族示例

**什么时候起作用**：确认是私有化 / AIO 后，需要知道"有哪些能力"时。

### 4. `scenario-dfr-vs-inspection.md` — 场景决策

**第二道门的依据。** 讲清 DFR 和巡检的本质差异：

- 核心对比表（触发源、时效、主接口、任务性质、数据流重点、载荷、后处理、人的角色）
- 场景决策树
- **错配红线表**：哪些搭配是错的、为什么错、正确做法是什么
- 共享组件（S3、Event API）vs 场景专属组件的划分

**什么时候起作用**：判断用户到底要做应急还是巡检时；用户把两个场景的做法搞混时。

### 5. `dfr-integration-architecture.md` — DFR 架构与选型

**仅覆盖 DFR / 应急场景。**

- 司空 2 在 DFR 中的角色
- 目标架构：告警 → 出警工作流 → 司空 2 → 机场执飞 → 直播/遥测/媒体/事件 → 下游系统
- 四大集成域优先级（P0 出警触发、P0 直播、P1 遥测、P2 媒体证据）
- 各接口详解：出警工作流（事件等级 1–5、默认阈值 3）、直播（RTMP/RTSP/WebRTC 选型表）、遥测（公有云转发 vs 私有化 MQTT Bridge、代表性 topic）、媒体证据、Event API（常见事件类型）
- 推荐的三阶段集成顺序

**什么时候起作用**：场景确定为 DFR 后。

---

### 6. `inspection-integration-architecture.md` — 巡检架构与选型

**仅覆盖巡检 / 巡逻场景。**

- 司空 2 在巡检中的角色（强调计划驱动、非告警驱动）
- 目标架构：航线规划 → 上传同步 → 计划任务 → 执飞 → 采集 → 存储 → AI 分析
- **巡检五步工作流**：飞行前准备 → 任务规划 → 数据采集 → 飞行执行 → 数据分析与共享
- 接口选型表（航线、计划任务、断点续飞、载荷切换、媒体、AI/VLM、三维重建）
- 各环节详解：基于点云/VME 的航线规划、可见光+热成像采集、周期调度模式
- 巡检的部署差异说明与安全数据护栏

**什么时候起作用**：场景确定为巡检后。

### 9. `integrate-with-existing-system.md` — 对接客户已有平台

**给"已经有一套系统，想把司空能力接进去"的用户用的。**

- **核心原则**：做适配层，而不是做第二个产品
- **三档集成深度**：L1 通知（收 Event API）/ L2 消费（拉数据、显示直播位置）/ L3 控制（从自己平台派遣）——并指出多数需求 L1+L2 就够
- **Demo 各部件能否复用对照表**：后端留、前端弃
- 账号权限打通、嵌入 UI（公有云不支持前端组件）、直播接入、事件接入、存储对接的分别指引
- 「先演示后集成」四阶段路线

**什么时候起作用**：用户提到"我们已经有 XX 系统"时。

### 10. `demo-localization.md` — 语言识别与文案本地化

**服务全球用户时用。**

- 语言识别优先级：显式指令 > 用户输入语言 > 项目既有约定 > 默认双语
- 该译什么（标题/按钮/提示/表单）、不该译什么（代码标识符、API 字段、Header、端点路径、日志）
- 运行时检测顺序：`?lang=` → localStorage → 浏览器语言 → 默认
- 数据驱动的双语文案模式（配置里存 `name` / `nameEn`）
- **按语言驱动功能默认值**：如中文用户默认高德、其他默认谷歌
- **安全文案铁律**：安全提示必须每种语言都有，英文缺失时宁可显示中文也不能丢
- 边界：本地化只改表现层，不得影响 API 选择、两道 Gate、安全护栏

**什么时候起作用**：用户用非中文提问时；生成含 UI 文案的代码时。
